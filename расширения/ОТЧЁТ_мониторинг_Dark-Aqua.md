# ОТЧЁТ: как работает связка Arena-агента — и наблюдательный прогон «Dark-Aqua»

> Дата: 2026-09-08, вечер. Автор: opencode (агент-наблюдатель).
> Задача прогона: диагностика «почему в System Monitor светлая рамка окна при теме Dark-Aqua».

---

## 1. Из чего состоит система (текущее состояние)

### 1.1 Три слоя связки

```
opencode / наблюдатель (я)
        │ задаёт задачу, НЕ вмешивается в цикл
        ▼
МОСТ LMArena_Bridge (arena_bridge.py, порт 8000)          ← запускает ТОЛЬКО пользователь
        │ Playwright → видимый Chrome → arena.ai (gemini-3-flash)
        │ POST /ask {"raw":true} — сырой ответ модели, БЕЗ внутреннего tool-loop
        ▼
ВНЕШНИЙ ЦИКЛ (auto_loop.py /tmp/opencode/monitor/)         ← мой скрипт наблюдения
        │ берёт ответ модели → executor → [RESULT] → обратно модели
        ▼
arena_executor.py --mode apply                             ← внешний исполнитель токенов
        │ [WRITE]/[EDIT]/[REGEX]/[READ]/[LIST]/[APPEND]/[DELETE]/[EXEC]
        ▼
Файлы и команды на машине пользователя
```

Ключевой принцип «raw-конвейера» (паспорт моста, п.7.1): мост — только транспорт
(вопрос → сырой текст ответа), а разбор и исполнение токенов делает внешний
executor. Это позволяет судить, кто виноват в сбое: транспорт, промт или инструмент.

### 1.2 Что ещё построено в рамках этой работы (Project/)

- **`arena_hands.py`** — единый скрипт «мозги+руки»: мозг Arena (через тот же
  `/ask raw`) строит план и выдаёт микро-команды; руки — локальная Gemma-4-e2b
  (GGUF, llama-cpp-python, /mnt/…/Program Files/ai models/suryeon123/AI-soo-Gemma-4),
  которая GBNF-грамматикой жёстко ограничена: может сгенерировать ТОЛЬКО валидный
  токен `[WRITE]/[READ]/[EXEC]` или `[DONE]` — «думать» физически не может.
  Бюджет 20 шагов, эскалации к мозгу при топтании. Self-test: 13/13 OK.
- **`arena_hands.sh`** — лаунчер (gnome-terminal, одно окно hands + окно Chrome);
  если мост не жив — поднимает его фоном (setsid nohup), ждёт готовность.
- Наблюдение этого вечера шло НЕ через arena_hands, а через классический
  raw-конвейер моста (модель на сайте сама формулирует токены) — чтобы валидировать
  боевую схему «мост + внешний executor» на реальной многошаговой задаче.

## 2. Прогон «Dark-Aqua»: хронология по раундам

Задача (дословно): «есть тема для Linux /home/egor/.themes/Dark-Aqua, в Nemo рамка
и 3 кнопки отображаются хорошо. Почему в системном мониторе рамка светлая? Проведи диагностику.»

Раунд 0: промт = arena_rules.txt (5591 симв.) + задача → `POST /ask {"raw":true}`.
Правила прицеплялись текстом в сообщение (raw-режим НЕ прицепляет файлы сам —
контракт из паспорта, п.28).

| Раунд | Ответ модели (токен) | Время | Исполнение (executor) | Наблюдение |
|---|---|---|---|---|
| 1 | `[LIST]/home/egor/.themes/Dark-Aqua[/LIST]` | 14.4с | OK: 6 каталогов (cinnamon, gtk-2.0/3.0/4.0, metacity-1, xfwm4…) | Чистый одиночный токен |
| 2 | `[EXEC]ls -d /home/egor/.config/gtk-4.0[/EXEC]` | 40.3с | OK (каталог существует) | Модель идёт верным следом: gtk-4.0-конфиг пользователя перекрывает тему |
| 3 | `[LIST]/home/egor/.config/gtk-4.0[/LIST]` | 38.6с | OK: settings.ini, gtk.css | — |
| 4 | `[EXEC]cat /home/egor/.config/gtk-4.0/settings.ini[/EXEC]` | 50.8с (после 502-ретрая) | OK | Первая 502 — пережита ретраем |
| 5 | `[READ]/home/egor/.config/gtk-4.0/gtk.css[/READ]` | 40.9с | OK, но контент МОJIBAKE | **ГЛАВНАЯ НАХОДКА, см. §3.1** |
| 6 | `[EXEC]gsettings get org.gnome.desktop.interface color-scheme[/EXEC]` | 76.7с | OK: `'prefer-dark'` | Модель проверяет системную цветовую схему |
| 7 | (запрос отправлен) | — | — | **502 дважды подряд → СТОП** |

Итого: 6 успешных раундов, 1 сбой на 7-м. Полное время активной работы ~5 минут.

### Поведение модели (gemini-3-flash): оценка

- **Протокол соблюдён идеально**: 6/6 ответов — ровно один валидный токен, ни одного
  туториала, ни одного «два токена», все теги закрыты. Правила в промте работают.
- **Стратегия диагностики — осмысленная**: тема (LIST) → пользовательский
  gtk-4.0-конфиг (перекрывает тему) → settings.ini → gtk.css → color-scheme.
  Это правильный след: libadwaita/GTK4-приложения игнорируют gtk-theme-name и
  читают ~/.config/gtk-4.0/gtk.css поверх темы; Nemo же рисует рамку через Muffin/CSD.
- Модель НЕ дошла до DONE: застряла на 6-м раунде из-за внешнего сбоя (мёртвая
  вкладка), а не из-за своего поведения. Дефицита итераций не было.

## 3. Находки прогона

### 3.1. ГЛАВНОЕ: пользовательский `~/.config/gtk-4.0/gtk.css` на диске — побит mojibake

Executor вернул содержимое в виде `ÐœÐµÑ…Ð°Ð½Ð¸Ð·Ð¼Ñ‹ --- Ð¾Ñ‚Ñ€Ð¸ÑÐ¾Ð²ÐºÐ¸…`.
Проверка показала: **файл на диске** (не транспорт!) реально содержит двойную
кодировку (UTF-8 → прочитанный как cp1252 → сохранённый снова UTF-8).
Ручная раскодировка (`text.encode('cp1252').decode('utf-8')`) восстанавливает
осмысленный русский комментарий:

> «Механизмы отрисовки рамок… Заставляем GTK4/libadwaita-приложения использовать…
> Nemo … Muffin … Server-Side Decorations … libadwaita по умолчанию игнорирует
> gtk-theme-name, заголовка окна…»

Выводы:
1. **Это и есть фактический ответ на вопрос пользователя о светлой рамке**:
   System Monitor — GTK3/libadwaita-приложение (в отличие от Nemo, который
   отрисовывает рамку через Muffin/SSD), и его вид определяет именно
   `~/.config/gtk-4.0/gtk.css` + `settings.ini`. Побитый/полурабочий gtk.css
   (плюс, возможно, неполное перекрытие стилей) даёт светлую рамку при
   color-scheme='prefer-dark' — тёмная схема применяется, а стили рамки из
   пользовательского css не догружаются корректно.
2. **Происхождение порчи**: файл был записан ранее (не этим прогоном!) — вероятно,
   тем самым историческим инцидентом mojibake (до фиксов 08.09), когда модель
   записала его через кривой сетевой канал. Т.е. это «шрам» на диске от старого
   бага, который сейчас и вскрывает диагностика. Текущий executor `_fix_mojibake`
   чинит только содержимое _ответов модели_, но НЕ делает inverse-фикс при READ
   побитого файла с диска.
3. **Улучшение для executor'а (кандидат в «Будущие исправления»)**: при READ/LIST
   детектить двойную кодировку в файле и (а) репортить модели пометкой
   `[MOJIBAKE ON DISK — decoded:]` + (б) предложить человеку починку отдельным
   действием. Иначе модель читает мусор и тратит раунды на его интерпретацию.

### 3.2. 502 на раундах 4 и 7: две разные причины

- Раунд 4: одиночный 502 — предположительно «молчаливый глоток хода» Arena
  (троттлинг сайта, известный п.27 паспорта). Ретрай в 20с вылечил.
- Раунд 7: двойной 502 → СТОП. В `arena_agent.log` причина однозначна:
  `Locator.count: Target page, context or browser has been closed` —
  **вкладка/окно Chrome моста было закрыто** (грабля №10 паспорта). Мост отвечает
  `/health ok` (сервер жив), но браузер мёртв → все ask падают. Лечение —
  только перезапуск моста пользователем. Автовосстановления в коде нет.

### 3.3. Тайминги raw-цикла

- Latency раунда (запрос→ответ модели): 14–77с, медиана ~40с. Это «ценак»
  одного хода через сайт. Шесть раундов — ~5 минут. Для сравнения: локальные
  руки (arena_hands, Gemma) генерируют токен за 5–12с — вот зачем нужен
  локальный субагент для простых операций.

### 3.4. Executor: замечаний к исполнению ноль

6/6 токенов исполнены корректно, deny-list не срабатывал (не было опасных команд),
вывод READ/LIST компактный, с номерами строк. Толерантность не потребовалась —
модель писала токены чисто.

## 4. Общая схема «как оно всё работает» (для будущего чтения)

1. **Пользователь** поднимает мост: `run arena_bridge.sh` → Chrome с arena.ai,
   сервер на :8000, модель на сайте выбрана (gemini-3-flash).
2. **Задача** формулируется и отправляется на `POST /ask {"raw":true}` c
   prepend `arena_rules.txt` (в raw-режиме мост правила НЕ цепляет — это контракт).
3. **Модель** отвечает ровно одним токеном (правила №2/№13 приучают).
4. **Внешний цикл** (auto_loop.py ИЛИ arena_hands.py ИЛИ руки Gemma) передаёт
   токен в `arena_executor.py --mode apply` (или исполняет сам).
5. **Executor** исполняет токен на ФС, возвращает текстовый отчёт.
6. Цикл оборачивает отчёт в `[RESULT]…[/RESULT]` + «выдай следующий ОДИН токен
   или DONE:» и отправляет снова на `/ask raw` — в ТОТ ЖЕ диалог Arena
   (единый чат, NEW_CHAT_PER_REQUEST=False).
7. Повтор до `DONE:` / лимита раундов / 502.
8. Проверка результата — НА ДИСКЕ, не по DONE модели.

## 5. Рекомендации

1. **Починить `~/.config/gtk-4.0/gtk.css`** (обратная раскодировка cp1252→UTF-8) —
   это, вероятно, устранит светлую рамку System Monitor'а; после правки проверить
   визуально. Файл стоит сначала скопировать в .bak.
2. **Executor**: добавить детект mojibake при READ и пометку модели.
3. **Мост**: грабля №10 (закрытая вкладка) — как и записано в паспорте, единственное
   лечение сейчас — рестарт пользователем; авто-`_new_chat`/reconnect в коде нет.
4. **Ретраи в цикле**: текущий (1 ретрай 20с) не справился с мёртвой вкладкой —
   можно различать «502 страница закрыта» (СТОП сразу, просить рестарт) от
   «502 молчание Arena» (ретрай).
