# Диагностика и решение проблемы: Яндекс Браузер отключает расширения

**Дата:** 2 августа 2026
**Файл отчёта создан для фиксации всех деталей разбора и решения.**

---

## 1. Суть проблемы (что жаловался пользователь)

В папке `/home/egor/Downloads/расширения` находятся несколько расширений, установленных в Яндекс Браузер вручную («распакованные» / unpacked, режим разработчика):

| Папка | Роль |
|---|---|
| `Magic Actions for YouTube/` | Расширение — переключение светлой/тёмной темы YouTube |
| `Copy URL Helper/` | Расширение — работа с плеером YouTube, «Magic Skip», восстановление вкладок |
| `take a screenshot/` | Расширение — скриншот текущей вкладки |
| `backup_prefs/` | НЕ расширение. Бэкапы файла Preferences браузера (`Preferences.backup`, `Preferences.backup2`) |

**Симптом:** Яндекс Браузер «постоянно» отключал расширения **Copy URL Helper** и **take a screenshot**, но НЕ трогал **Magic Actions for YouTube**. Пользователь заявлял, что все расширения для него критически важны, и просил глубокую диагностику с причинами.

### 2.4. Вычисление ID расширений (ключевой шаг)
Написан Python-скрипт, который воспроизводит алгоритм Chromium для вычисления ID расширения двумя способами:

1. **ID из `key`** — когда в манифесте есть поле `key` (RSA-публичный ключ в DER/base64):
   - `ID = первые 16 байт SHA-256(DER-ключ)`, каждый байт превращается в две буквы из алфавита `abcdefghijklmnop` (старший и младший полубайт).
2. **ID из пути** — когда поля `key` НЕТ (обычные распакованные расширения):
   - `ID = первые 16 байт SHA-256(абсолютный путь к папке)`, тем же способом.

## 3. Корневая причина (подробно)

### 3.1. Поле `key` в манифесте = фиксированный ID
В `manifest.json` расширений **Copy URL Helper** и **take a screenshot** присутствовало поле:

```json
"key": "MIIBIjANBgkqhkiG9w0BAQEFAAOCAQ8AMIIBCgKCAQEA..."
```

Это поле (публичный ключ) заставляет браузер вычислять ID расширения из самого ключа, а НЕ из пути. ID получается постоянным независимо от того, где лежит папка.

Расширение без `key` (как Magic Actions for YouTube) получает ID, производный от **абсолютного пути** папки, в которой оно лежит.

### 3.2. Два «издания» одного расширения в профиле
По таймлайну из меток времени (Chromium-время в микросекундах от 1601-01-01, переведено в реальные даты):

| Событие | Дата и время |
|---|---|
| Copy URL Helper установлен как расширение «из пути» (`ncfnpac…`) | 2026-07-31 08:43 |
| take a screenshot установлен как расширение «из пути» (`hknocip…`) | 2026-07-31 08:42 |
| Copy URL Helper переустановлен — появился ID «из ключа» (`dgkii…`) | 2026-07-31 10:02 |
| take a screenshot переустановлен — появился ID «из ключа» (`pebjgi…`) | 2026-07-31 14:51 |
| Magic Actions for YouTube установлен | 2026-08-02 09:52 |
| Последнее обновление Copy URL Helper / take a screenshot («из ключа») | 2026-08-02 09:53 |

**Хронология событий:**
1. Сначала оба расширения были загружены **без** `key` → браузер присвоил ID из пути (`ncfnpac…`, `hknocip…`).
2. Позже в манифесты был **добавлен `key`** (и расширения перезагружены) → браузер вычислил **новые** ID из ключа (`dgkii…`, `pebjgi…`) и завёл для них новые записи в `Preferences`.
3. Старые записи «из пути» остались в профиле как **«сироты»** на том же самом пути, и браузер пометил их как отключённые с `disable_reasons = [1]`.

### 3.3. Что означает `disable_reasons = [1]`
Битовая маска из Chromium:
- `1` = `DISABLE_USER_ACTION` (расширение отключено/помечено как отключённое в ходе действий браузера над его состоянием).

То есть старое «издание» было выключено, а новое (из ключа) — включено. Но обе записи указывали на **один и тот же путь**.

### 3.4. Почему браузер «постоянно» отключал
При каждом запуске браузер сканирует распакованные расширения: читает `manifest.json` по пути из записи, заново вычисляет ID и сверяет с сохранённым. Логика:

- Запись `ncfnpac…`: манифест теперь содержит `key` → вычисленный ID = `dgkii…` ≠ сохранённому `ncfnpac…` → **запись признаётся несоответствующей и отключается**.
- Запись `dgkii…`: вычисленный ID совпадает → загружается.

Однако на один путь теперь претендуют **две записи с разными ID**. В меню расширений пользователь видит **два «Copy URL Helper»** и **два «take a screenshot»**: один включён, второй выключен. Состояние этой связки нестабильно и переоценивается при каждом старте/перезагрузке — отсюда субъективное ощущение «браузер постоянно отключает мои расширения».

### 3.5. Почему Magic Actions for YouTube не трогали
В его манифесте **нет поля `key`**, поэтому в профиле существует **ровно одна** запись, а её ID всегда совпадает с вычисляемым из пути. Конфликта нет — расширение никогда не отключается. Это и есть главное отличие «выживающего» расширения от «отключаемых».

### 3.6. Второстепенные факторы (усугубляющие, но не причины)
- У проблемных расширений **широкий набор прав**: `activeTab`, `scripting`, `tabs`, `windows`, `sessions`, `clipboardWrite` (+ `downloads` у скриншотера). Браузеры относятся к ручным расширениям с большим набором прав настороженнее.
- Папка лежит в `~/Downloads/расширения`. Так как ID «из пути» зависит от пути, любое переименование/перенос папки в будущем снова «сбросит» расширения (изменится ID).
- В профиле остались следы расширения `Kimi` (`hinhmbbmelmmgiehkfmmkmfndadahmkk`) со старой машины по пути `/mnt/807EB5FA7EB5E954/soft/.../Kimi`, который на этой машине не существует — поэтому оно корректно отключено (`disable_reasons: [1]`). К нашей проблеме отношения не имеет, но объясняет одну «непонятную» отключённую запись в бэкапах.
- Проверка: оба `key` НЕ соответствуют существующим расширениям Chrome Web Store (страницы `chromewebstore.google.com/detail/<id>` возвращают «empty-title»), т.е. это не извлечённые из магазина расширения, а самодельные.

## 6. Рекомендации на будущее

1. **Не добавлять `key` в манифесты** распакованных расширений, если они уже загружались без него — это создаёт второе «издание» с другим ID.
2. **Не менять расположение папок.** Без `key` ID расширения зависит от пути: переименование или перенос папки = новый ID = «расширение слетает». Рекомендуется перенести папку в постоянное место, например `~/.local/share/расширения/` или `~/Расширения/`, и в дальнейшем не двигать.
3. **Перед правкой `Preferences`** всегда полностью закрывать браузер и делать резервную копию файла.
4. Периодически чистить «мёртвые» записи в `Preferences` (как случай с `Kimi` со старой машины), чтобы профиль не копил мусор.
